# Файловая структура лабораторной

Объяснение основано на текущем коде репозитория. Наличие модулей и конфигурации не подтверждает успешный запуск контейнеров, прохождение CI или качество обученной модели: это проверяется отдельно.

## Общая схема

В проекте два основных процесса: подготовка и обучение модели, затем обслуживание запросов уже обученной моделью.

```text
data/raw/WELFake_Dataset.csv
    ↓ ml/data.py — очистка и разбиение
data/processed/{train,validation,test}.csv + manifest.json
    ├── ml/eda.py — анализ данных
    └── ml/train.py — обучение и validation
            ↓
         MLflow: runs, datasets, metrics, artifacts, logged models
            ↓ ml/register.py — регистрация и назначение alias
         Model Registry: fake-news-classifier, версии, champion
            ├── ml/evaluate.py — финальная оценка конкретной версии на test
            └── app/model.py — загрузка выбранной версии при старте
                    ↓ app/db.py — сохранение в app.state
                 app/routes.py — POST /process
```

## app/: обработка HTTP-запросов

### app/main.py

Точка входа для `uvicorn app.main:app`. Создаёт объект FastAPI, читает версию приложения из `pyproject.toml`, настраивает логирование, подключает роутеры и обработчик жизненного цикла `lifespan`.

### app/routes.py

Содержит HTTP-маршруты и схемы входных/выходных данных:

| Маршрут | Ответственность |
| --- | --- |
| `POST /process` | Проверить входной текст, вызвать `predict`, вернуть класс и версию модели |
| `GET /healthz` | Ответить, что запущенное приложение обрабатывает запросы |
| `GET /api/v1/version` | Вернуть версию приложения |
| `GET /api/v1/health` | Проверить соединение с PostgreSQL приложения |

Для `/process` нужна непустая строка `text` длиной до 50000 символов после удаления пробелов по краям. `predict` выполняется в threadpool. Модель здесь не обучается и не скачивается заново для каждого запроса.

`/healthz` не выполняет отдельной проверки MLflow или БД на каждый вызов. `/api/v1/health` проверяет PostgreSQL, а не всю ML-инфраструктуру.

### app/model.py

Читает `MLFLOW_TRACKING_URI`, `MODEL_NAME` и `MODEL_ALIAS`. Находит версию по alias, загружает sklearn-модель по точному номеру и проверяет наличие классов `0` и `1`. Возвращает модель, имя и номер версии. Смысл меток должен быть согласован с обучением: `0=real`, `1=fake`.

Этот файл отвечает на вопрос: «Какую модель приложение должно использовать?»

### app/db.py

Несмотря на название, сейчас отвечает за жизненный цикл и БД, и модели. Перед началом обслуживания запросов создаёт SQLAlchemy engine, вызывает загрузчик модели и сохраняет результаты в `app.state`. При завершении очищает ссылку на модель и освобождает ресурсы engine. Ошибка загрузки модели прерывает startup.

### app/__init__.py

Обозначает каталог как Python-пакет; отдельной бизнес-логики в нём нет.

## ml/: данные, обучение и управление версиями

| Файл | Что делает |
| --- | --- |
| `smoke.py` | Создаёт проверочный run, логирует параметр, условную метрику и файл, затем скачивает файл обратно. Настоящего обучения здесь нет |
| `data.py` | Скачивает исходник при запросе, проверяет MD5, очищает данные, разбивает их и сохраняет manifest с SHA-256 |
| `eda.py` | Анализирует train: баланс классов, длины текстов, результаты очистки. Сохраняет графики и наблюдения в MLflow |
| `train.py` | Обучает выбранный Pipeline на train, оценивает на validation и сохраняет модель в MLflow |
| `common.py` | Общие операции: настройка MLflow, логирование datasets, исходников, метаданных и результатов оценки |
| `register.py` | Регистрирует сохранённую модель или назначает alias существующей версии |
| `evaluate.py` | Оценивает конкретную зарегистрированную версию на test отдельным run |

В `data.py` удаляются пустые тексты, невалидные метки, конфликтующие записи и точные повторы нормализованного текста. Разбиение — примерно 70/15/15, со стратификацией и seed=42. Близкие перепечатки автоматически не исключаются. При чтении подготовленной выборки проверяется её SHA-256.

В `train.py` реализованы варианты:

- `dummy`: TF-IDF и DummyClassifier с выбором наиболее частого класса — простая точка сравнения.
- `baseline`: TF-IDF по отдельным словам и LogisticRegression с `C=1.0`.
- `bigram`: TF-IDF по отдельным словам и парам слов, LogisticRegression с `C=1.0`.
- `c01`: TF-IDF по отдельным словам и LogisticRegression с `C=0.1`.

TF-IDF обучается внутри Pipeline только на train. Validation используется для сравнения вариантов. `train.py` сохраняет модель через `mlflow.sklearn.log_model`, но не назначает автоматически `champion`.

`common.py` сохраняет метрики, classification report, confusion matrix и CSV ошибок. Также логирует manifest, Git commit, признак незакоммиченных изменений и исходники для прослеживаемости.

`evaluate.py` проверяет соответствие manifest обучающему run, загружает точную версию и считает `test_*` метрики. Test предназначен для финальной оценки уже выбранной модели.

## data/: исходные данные и их происхождение

- `data/README.md` описывает источник, подготовку и ограничения данных.
- `data/label-audit.json` содержит аудит значения меток. В проекте явно зафиксировано противоречие с описанием карточки источника и принята интерпретация `1=fake`, `0=real`. Это не независимая проверка истинности всех новостей.
- `data/raw/` предназначен для исходного CSV и метаданных его скачивания.
- `data/processed/` содержит результаты подготовки: train, validation, test и `manifest.json`.
- `docs/hw3-data-manifest.json` — сохранённая в репозитории запись о подготовке данных: количества строк, hashes и настройки. Загрузчик обучения по умолчанию читает manifest из `data/processed/`, а не эту копию.

Dataset Tracking в данном коде логирует метаданные datasets и связь с run. Его не следует считать резервной копией исходного CSV.

## Docker и хранение результатов

Корневой `Dockerfile` собирает образ API: устанавливает зависимости, копирует `app/`, запускает Uvicorn. Обученная модель в образ не копируется — загружается из MLflow при старте.

`infra/mlflow/Dockerfile` собирает отдельный образ MLflow с PostgreSQL-драйвером.

`docker-compose.yml` описывает четыре сервиса:

| Сервис | Назначение |
| --- | --- |
| `app` | FastAPI, порт компьютера `8001` |
| `db` | PostgreSQL приложения, порт компьютера `5433` |
| `mlflow` | Tracking Server, UI, Registry и доступ к артефактам, порт `5000` |
| `mlflow-db` | PostgreSQL с метаданными MLflow, без публикации порта на компьютер |

В текущем коде `/process` не сохраняет запросы или предсказания в `db`: эта БД используется проверкой `/api/v1/health`. Модели и runs обслуживает другая часть системы — MLflow.

Compose подключает постоянные volumes:

- `postgres_data`: данные PostgreSQL приложения.
- `mlflow_postgres_data`: метаданные MLflow — runs, параметры, метрики, записи Registry.
- `mlflow_artifacts`: файлы артефактов, включая сохранённые модели.

`run_container.sh` переходит в корень проекта и выполняет `docker compose up -d --build app`. Зависимости сервиса поднимаются средствами Compose, но скрипт не обучает и не регистрирует модель: `champion` нужно подготовить заранее.

## Настройки окружения и зависимостей

| Файл | Назначение |
| --- | --- |
| `pyproject.toml` | Зависимости и группы `web`, `ml`, `dev`, версия приложения, настройки Ruff и coverage |
| `uv.lock` | Точные разрешённые версии зависимостей для воспроизводимой установки |
| `.python-version` | Версия Python для инструментов установки |
| `env.example` | Пример адресов и настроек для запуска с компьютера |
| `.env` | Локальные значения; сам Python-код не загружает этот файл явно |
| `.gitignore` | Исключения из Git: локальные данные, окружение, кэш, секреты |
| `.dockerignore` | Исключения из контекста Docker build |
| `.pre-commit-config.yaml` | Локальные проверки перед коммитом, если hooks установлены |

В Compose адреса и настройки сервисов заданы явно через `environment`. Не следует считать, что любое изменение `.env` автоматически изменит эти значения.

## tests/ и GitHub Actions

| Файл | Что проверяет |
| --- | --- |
| `tests/conftest.py` | Общая fixture подменяет загрузку настоящей модели тестовым объектом |
| `tests/test_data.py` | Очистку, mapping меток, воспроизводимость и непересечение split, обнаружение изменения CSV |
| `tests/test_inference.py` | Контракт `/process`, валидацию текста, повторное использование модели, выбор точной версии по alias и ошибку startup |
| `tests/test_routes.py` | Health-маршруты и версию приложения; проверка настоящего PostgreSQL требует `DATABASE_URL` |
| `.github/workflows/ci.yml` | Установку зависимостей, Ruff, форматирование, pytest и отчёт покрытия; поднимает тестовый PostgreSQL |
| `.github/workflows/cd.yml` | После проверок для тега `v*` сверяет версию и публикует Docker-образ API в GHCR |

Unit-тесты модели используют подмены и не доказывают реальное переключение alias в работающей системе. CD здесь публикует образ, но не разворачивает приложение на сервере и не выбирает модель в Registry.

## Как рассказать структуру на защите

> В `ml/` находится подготовка данных, обучение, логирование результатов, регистрация и оценка моделей. `data/` содержит описание происхождения данных и локальные выборки. `app/` — FastAPI: при запуске он выбирает модель через champion, загружает её из MLflow и использует в POST /process. Docker Compose запускает API, MLflow и две PostgreSQL с разными назначениями. Тесты проверяют код, CI запускает проверки, а CD публикует образ API. Версию модели можно сменить через alias и перезапуск приложения без изменения inference-кода.
