# HW3: план реализации в этом проекте

Это исходный план и чеклист реализации, составленный 16 октября 2026 года. Состояние до начала работы описано ниже; фактические проверки и результаты реализации находятся в [отчёте](hw3-results.md). Требования: [hw3.md](hw3.md). Учебные объяснения и упражнения: [hw3-mlflow-guide.md](hw3-mlflow-guide.md).

## От чего отталкивались

Уже есть FastAPI, PostgreSQL, Docker Compose, uv, Ruff, pytest и CI. В `app/db.py` есть `lifespan`, подключённый в `app/main.py`. В `app/routes.py` есть `/healthz` и служебные ручки с префиксом `/api/v1`.

До реализации в просмотренных файлах не было MLflow, датасета, обучения, Registry и `/process`. На момент начала подготовки плана `README.md` был пустым; теперь в нём ссылки на учебные документы. Существующие тесты с `TestClient` запускают lifespan; часть тестов требует работающий PostgreSQL. Следовательно, добавление обязательной загрузки модели затронет и тестовый запуск приложения.

## Результат и принятые решения

Сделать локальный учебный стенд: обучение запускается с компьютера, MLflow и БД работают в Compose, существующий FastAPI получает модель из Registry. Это позволяет разбирать Python-код отдельно от сборки контейнеров.

```text
CSV → очистка и фиксированные train / validation / test
                      ↓
             Python: EDA и обучение
                      ↓ HTTP
             MLflow Tracking + UI
              ├── PostgreSQL: метаданные и Registry
              └── Docker volume: артефакты и файлы моделей
                      ↓
          fake-news-classifier@champion
                      ↓ загрузка при старте
            существующий FastAPI → POST /process
```

| Решение | Зачем |
| --- | --- |
| MLflow 3.x с закреплённой точной версией при реализации | Одинаковые версии сервера и клиентов; воспроизводимый запуск |
| Отдельный сервис `mlflow-db` на PostgreSQL 17 | Не смешивать служебные таблицы MLflow с БД приложения |
| Именованный volume `mlflow_artifacts` | Отдельное от PostgreSQL хранилище файлов, сохраняющееся при пересоздании контейнера |
| Передача артефактов через MLflow server | Клиентам не нужно монтировать серверный каталог |
| TF-IDF + LogisticRegression в одном sklearn Pipeline | Обучение и inference используют один сохранённый preprocessing |
| Ручное логирование первых экспериментов | Видно, какой вызов создаёт параметр, метрику, артефакт и связь с данными |
| Alias `champion` | Переключать рабочую версию без изменения Python-кода |

Backend Store и Artifact Store здесь раздельные: PostgreSQL и файловый volume. Это не отдельный S3-сервис. В задании S3/MinIO явно не требуется; если на курсе под Artifact Store подразумевают объектное хранилище, заменить volume на S3-совместимое хранилище до сдачи. Клиентский код при проксировании останется тем же. Архитектура хранения описана в [документации MLflow](https://mlflow.org/docs/latest/self-hosting/architecture/overview/).

## Какие файлы появятся

Структура реализации; дополнительно есть `ml/common.py` с общими операциями логирования и `ml/smoke.py` для первого run:

```text
ml/
  __init__.py
  data.py              # загрузка, проверки, очистка, сохранение split
  eda.py               # графики и выводы в MLflow
  train.py             # Pipeline, обучение, метрики, модель
  register.py          # выбранная модель → Registry → alias
  evaluate.py          # финальная оценка выбранной версии на test
infra/mlflow/
  Dockerfile           # MLflow фиксированной версии + PostgreSQL driver
data/
  README.md            # источник, метки, получение и ограничения данных
  raw/                 # исходный CSV, вне Git
  processed/           # фиксированные split, вне Git
tests/
  test_inference.py    # API, lifespan и ошибки без настоящего MLflow
docs/
  hw3-results.md       # фактические результаты, заполняется после запусков
```

Из существующих файлов понадобятся `docker-compose.yml`, `pyproject.toml`, `uv.lock`, `Dockerfile`, `env.example`, `.gitignore`, `app/db.py`, `app/routes.py`, тесты и CI. `README.md` станет точкой входа с проверенными командами. Классы-обёртки над MLflow и универсальный framework обучения для этой работы не нужны.

## Этап 1. Поднять MLflow и записать пробный run

**Сделать:**

- [ ] Добавить группу зависимостей `ml`: `mlflow`, `pandas`, `scikit-learn`, `matplotlib`. Закрепить разрешённые версии в `uv.lock`; версию MLflow явно согласовать с серверным образом.
- [ ] Добавить `mlflow-db`, `mlflow`, volumes для метаданных и артефактов, healthcheck БД и ожидание готовности БД сервером.
- [ ] В серверном образе установить совместимый PostgreSQL driver; например, `psycopg2-binary` с URI `postgresql+psycopg2://...`.
- [ ] Опубликовать MLflow на `127.0.0.1:5000`, существующий API оставить на `127.0.0.1:8001`.
- [ ] Использовать `--backend-store-uri`, `--serve-artifacts`, `--artifacts-destination /mlartifacts`; volume смонтировать именно в `/mlartifacts`.
- [ ] Разрешить Host для `localhost`, `127.0.0.1` и `mlflow` с нужными портами через `--allowed-hosts`; сверить формат с CLI выбранной версии.
- [ ] Записать `smoke` run с параметром, метрикой и текстовым артефактом; открыть всё в UI.

| Кто обращается к серверу | `MLFLOW_TRACKING_URI` |
| --- | --- |
| Python на компьютере | `http://127.0.0.1:5000` |
| FastAPI внутри Compose | `http://mlflow:5000` |

Серверный URI PostgreSQL синхронный; существующий `DATABASE_URL` приложения с `asyncpg` не копировать в MLflow. Внутри контейнера `localhost` обозначает этот контейнер.

**Готово, когда:** run виден в UI, артефакт скачивается клиентом, а после перезапуска контейнеров данные остаются. До этого не переходить к обучению. Ориентир: [Tracking Server](https://mlflow.org/docs/latest/self-hosting/architecture/tracking-server/).

## Этап 2. Зафиксировать данные и разбиение

Рабочий вариант — англоязычный [WELFake на Zenodo](https://zenodo.org/records/4561253). Это предложение для проекта, а не уже скачанный и проверенный датасет. В описании авторов указано `0 = fake`, `1 = real`; соответствие меток нужно сверить с документацией скачанной версии и примерами, прежде чем писать преобразование. Ручной просмотр примеров не заменяет проверку разметки всего корпуса. При реализации обнаружено противоречие между описанием и CSV; принят исходный fake=1, см. [аудит и пояснение](../data/README.md).

- [ ] В `data/README.md` сохранить URL записи и файла, дату получения, лицензию из карточки, названия столбцов и смысл меток. Не рассчитывать число строк по описанию сайта: посчитать при чтении CSV.
- [ ] Привести вход к `row_id`, `text`, `label`; внутреннее соглашение проекта: `0 = real`, `1 = fake`. Явно записать преобразование исходных меток, не перезаписывать оригинальный CSV.
- [ ] Для первого варианта брать только тело новости: API тоже принимает одно поле `text`. `title` можно изучить в EDA, но не подмешивать незаметно в модель.
- [ ] Удалить пустые тексты и невалидные метки с подсчётом причин. Не превращать NaN в строку `"nan"`.
- [ ] Найти повторы нормализованного текста; конфликтующие метки исключить с отчётом, одинаковые повторы свести к одной записи **до split**.
- [ ] Сделать фиксированные стратифицированные train/validation/test = 70/15/15, `random_state=42`; сохранить CSV, `row_id`, SHA-256 файлов, конфигурацию и счётчики очистки в manifest.
- [ ] Проверить отсутствие пересечений `row_id` и нормализованных текстов между split. Сохранить manifest как артефакт.

Для технической проверки можно взять фиксированную небольшую стратифицированную подвыборку. Помечать её `purpose=smoke`, сохранять её состав и не сравнивать её метрики с полным датасетом как равнозначные.

**Готово, когда:** повторный запуск подготовки на том же исходном файле даёт те же split; понятны потери строк и смысл каждого класса. Точные повторы исключены; риск близких перепечаток и зависимости от источника описан отдельно.

- [ ] В каждом обучающем run вызывать `mlflow.data.from_pandas(...)` и `mlflow.log_input(...)` для фактически использованных train и validation с разными context.

**Готово, когда:** из любого training run можно понять, откуда данные, какое разбиение использовано и какой код его подготовил. Различия source/digest/lineage разобраны в [учебном руководстве](hw3-mlflow-guide.md#4-как-отслеживать-данные).

## Этап 4. Провести сравнимые эксперименты

Сначала зафиксировать протокол, затем смотреть результаты. Для всех основных runs использовать одни и те же split, seed, входное поле `text` и ограничения словаря.

| Run | Модель | Изменение и вопрос |
| --- | --- | --- |
| `control-dummy` | DummyClassifier(strategy="most_frequent") | Что получится вообще без анализа текста? Дополнительный контроль |
| `baseline-unigram` | TF-IDF + LogisticRegression, C=1 | Базовый обучаемый вариант |
| `variant-bigram` | Тот же Pipeline, ngram_range=(1, 2) | Помогают ли сочетания двух слов? |
| `variant-c01` | Как baseline, C=0.1 | Помогает ли более сильная регуляризация? |

Таким образом, есть baseline и два варианта даже без учёта DummyClassifier. Для первых трёх TF-IDF runs: `max_features=30000`, `min_df=2`, `max_iter=1000` у LogisticRegression. Это стартовые решения, а не обещание оптимального качества. Не скрывать предупреждения о несходимости.

- [ ] Основная метрика выбора — `val_f1_macro`: одинаковый вес обоим классам, поскольку стоимость ошибок пока не задана.
- [ ] Дополнительные: `val_accuracy`, `val_precision_fake`, `val_recall_fake`, `val_f1_fake`, `fit_seconds`. Для fake-метрик явно `pos_label=1` и выбранный `zero_division`.
- [ ] Логировать настройки TF-IDF/классификатора, seed, размеры split, версию preprocessing, Git commit и признак незакоммиченных изменений.
- [ ] Сохранить confusion matrix с подписями классов, classification report, CSV ошибок validation, полный Pipeline, signature и input example.
- [ ] Параметры логировать явно; сначала обойтись без autolog, чтобы понимать состав run.
- [ ] Сравнить runs в UI; сохранить таблицу реальных результатов и объяснение выбора в `docs/hw3-results.md`.

**Готово, когда:** результаты сравнимы, у каждой гипотезы есть измеренный ответ. Улучшение не обязательно: неудачный вариант тоже полезный эксперимент. Test не участвует в выборе. При почти одинаковом `val_f1_macro` разумно выбрать более простой вариант и явно объяснить решение.

## Этап 5. Registry и финальная оценка

- [ ] Логировать модели через `mlflow.sklearn.log_model(..., name="model", ...)`; сохранить возвращённый `model_uri` в теге run `logged_model_uri`.
- [ ] Зарегистрировать baseline и выбранный вариант под одним именем `fake-news-classifier`. Получить две версии, связанные с соответствующими runs. Если baseline победил, второй вариант остаётся challenger.
- [ ] Взять реальные номера версий из результата регистрации; не считать, что они обязательно равны 1 и 2.
- [ ] Назначить `champion` выбранной версии. Сохранить причину выбора и mapping меток в описании/артефактах.
- [ ] Загрузить выбранную версию по её номеру и один раз оценить на test. В отдельный run `final-test` записать входной test dataset, `test_*` метрики и точную версию модели.
- [ ] После просмотра test не подбирать заново параметры на этом же test. Честно описать ограничения: английский корпус, случайный split, возможные признаки издателя и отсутствие проверки фактов по внешним источникам.
- [ ] Повторить `predict` после загрузки из MLflow и сравнить с предсказанием исходного Pipeline на тех же строках.

**Готово, когда:** видны минимум две версии; `models:/fake-news-classifier@champion` разрешается в выбранную; сохранённый Pipeline воспроизводит предсказания. Ориентир: [Model Registry Workflows](https://mlflow.org/docs/latest/ml/model-registry/workflow/).

## Этап 6. Подключить существующий FastAPI

- [ ] Расширить существующий `lifespan` в `app/db.py`, сохранив освобождение engine в `finally`. Загрузку модели делать до `yield` внутри защищённого блока; не создавать второй независимый lifespan.
- [ ] Один раз разрешить alias в номер версии, затем загрузить `models:/fake-news-classifier/<version>`. Сохранить Pipeline и точную версию в `app.state`; использовать `mlflow.sklearn.load_model`.
- [ ] При недоступной модели/alias завершать startup с понятной ошибкой. Не подменять модель DummyClassifier без уведомления.
- [ ] Добавить `async def` для **`POST /process`** в `router` без `/api/v1`, чтобы совпасть с буквальным требованием задания.
- [ ] Принять `{"text": "English news text"}`; отклонять пустые/пробельные строки и слишком длинный ввод, например более 50000 символов.
- [ ] Выполнить синхронный `predict` через `run_in_threadpool`, вернуть `label`, `model_name`, `model_version`. На запрос не обращаться в MLflow.
- [ ] В `env.example` описать `MLFLOW_TRACKING_URI`, `MODEL_NAME=fake-news-classifier`, `MODEL_ALIAS=champion`; добавить runtime-зависимости модели в образ приложения. Текущий Dockerfile устанавливает только base + `web`, группа `ml` сама в образ не попадёт.
- [ ] Добавить зависимость готовности API от MLflow в Compose. Сначала поднимать MLflow, затем обучать/регистрировать модель, затем запускать API.

Для учебной реализации допустимо устанавливать группу `ml` целиком и в API: это проще, хотя образ станет больше. Отдельный минимальный inference-набор зависимостей можно выделить позже. MLflow не пересоздаёт Python-окружение при обычном `sklearn.load_model`; совместимые пакеты должны быть в образе.

**Готово, когда:** два запроса используют одну загруженную модель; после переноса alias API продолжает обслуживать старую версию до перезапуска, а после перезапуска показывает новую. Один раз при старте означает один раз **на процесс/worker**; демонстрацию проводить с одним worker.

## Этап 7. Проверки и защита

- [ ] В unit-тестах замокать получение версии и загрузку модели до входа в `TestClient`; проверить одну загрузку на lifespan при нескольких запросах.
- [ ] Проверить контракт `/process`, отклонение пустого/длинного текста, соответствие label и ошибку startup при отсутствии модели.
- [ ] Адаптировать существующие тесты к обязательной модели; CI для них не должен требовать настоящего Registry. Существующую проверку PostgreSQL оставить интеграционной.
- [ ] Один раз вручную пройти полный путь с настоящими сервисами: подготовка → EDA → runs → Registry → test → API; замоканные тесты его не заменяют.
- [ ] Проверить сохранность артефактов после перезапуска; записать в README последовательность запуска и восстановления.
- [ ] Запустить Ruff, pytest и актуальную сборку Compose после изменения зависимостей. Не добавлять обучение полного датасета в каждый CI-запуск.
- [ ] Заполнить `hw3-results.md`: реальные run IDs, таблица метрик, версии, выбранный alias, источник данных, ограничения и скриншоты UI.

Порядок показа на защите: источник данных → dataset input конкретного run → сравнение трёх обучаемых runs → график/ошибки → две версии в Registry → `champion` → `/process` → перенос alias и перезапуск API.

## Рекомендуемый темп

| Занятие | Фокус | Видимый результат |
| --- | --- | --- |
| 1 | Сервер и smoke run | Параметр, метрика и артефакт в UI |
| 2 | Данные, очистка, EDA, tracking | Split manifest, графики, dataset inputs |
| 3 | Pipeline и сравнение гипотез | Baseline + два варианта, фактическая таблица |
| 4 | Registry и финальный test | Версии, alias и test-отчёт |
| 5 | API и демонстрация | `/process`, тесты, воспроизводимый README |

Ориентир — занятия по 1–2 часа, но это не оценка гарантированного срока: первый Docker/MLflow setup и разбор данных могут занять больше. После каждого занятия пройти соответствующее упражнение из [руководства](hw3-mlflow-guide.md).
